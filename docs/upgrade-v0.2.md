# 从 v0.1.0 升级到 v0.2.0

1. 停止旧版服务，并确认没有另一个进程继续使用同一个数据库。不要让旧、新服务同时读写同一份 `data/`。
2. 备份完整 `data/` 目录和 `.env`。必须在停服后复制，保留可能存在的 SQLite WAL/SHM 文件；不要只复制一个正在写入的 `.sqlite` 文件。
3. 将 v0.2.0 解压到独立目录，把旧版 `data/` 与 `.env` 复制到新目录。不要用新目录的配置样例覆盖原凭证和真实能力绑定。
4. 在新目录执行 `npm.cmd test`，然后执行 `npm.cmd start`。已有 `auth.local.json` 的升级场景**不运行 init**；初始化会拒绝覆盖原凭证。
5. 登录原身份，检查流程、审批、运行记录、预算、事件收件箱与拒收名单。先核验真实只读 Worker，再考虑恢复真实商业动作。

启动自动执行事务型、增量式 schema 1 → 2 迁移，增加批次、关联绑定和事件路由表，不重写既有运行/流程/审批 JSON。旧版待消费事件保留为 unmatched；旧运行进入等待节点时以原真实回执重新绑定。版本不识别时拒绝启动。

v0.2 的运行对象增加可选 batchId/sourceRunId/targetEmail/deadlineAt，以及继承步骤来源。既有单客户运行不需要重新创建。升级后同一个 `correlationId` 不能对应多个运行；旧网关若复用标识会被阻断，必须先修正网关，不是忽略错误。

数据库一旦迁移到 schema 2，v0.1 会拒绝打开。回滚需要停止新版、切回旧程序并恢复升级前完整备份；仅回退代码不能回退数据库。旧备份不包含升级后的真实业务结果，恢复后必须先与网关对账，避免再次执行已经发生的商业动作。

真实 v0.1 ZIP 跨版本检查已验证：保存原运行及审批、迁移待回复任务、消费升级前已存事件、不重复派发发送、审计链保持有效。测试使用合成外部服务输出，不意味着用户企业数据已在此环境迁移。Windows 和 Docker 的现场升级尚未验收。
