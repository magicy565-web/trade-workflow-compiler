# 客户开发批次（v0.2）

## 执行方式

买家开发仍是已发布的 WorkflowSpec v1。研究、发现、筛选只执行一次。筛选返回多个买家时，运行在起草开发信之前进入 `BATCH_READY`，不擅自选择第一个买家，也不让 Worker 批量发送。

操作者在运行卡片点击“选择客户并创建批次”，核对真实研究结果、来源和邮箱，手动选择 1–50 位客户。系统会创建独立子任务，每个任务只继承一位买家的筛选结果。继承步骤标记 `inheritedFromRunId`，不是假装重新执行了研究。

每位客户分别经过起草、具体内容审批、发送、等待首条有效回复、分类。审批仍要求独立 approver。起草 Worker 不能换成另一个收件人，网关回执中的收件人也必须与审批一致。

创建全部子任务、取消原任务、登记批次与审计记录处于同一个 SQLite 事务。原任务不会再多发一封。相同创建幂等键返回同一批次；同一源任务不能创建第二批。**未被选中的买家不会自动发信；本版不支持给已有批次追加客户。**

## 预算与期限

批次继承原流程已审批的总预算，不给每位客户复制一份新预算。

```
原任务已预留费用 + 所选客户数 × 每位客户剩余节点最坏预留费用 <= 原授权预算
```

每个节点派发前在同一事务内预留子任务和共享批次预算。并发派发不能越过这个内部预留上限。服务商报告费用超出节点预留时，系统停止该任务并暂停批次；这不等于能替外部服务商强制封顶账单。没有收到费用回执的调用也不能据此当作免费。

子任务继承原任务的授权截止时间，不借拆分批次重新获得一个月的执行期。

## 暂停、恢复、取消

暂停阻止后续派发，不取消已经在远端运行的动作。恢复保留节点、审批和预算；存在结果不明的外部动作时不能直接恢复。取消批次会停止未完成子任务；已派发但不确定结果的动作进入 `NEEDS_RECONCILIATION`。已取消批次不能恢复。

外部动作结果不明时不会自动重发。独立审批人在任务卡片提交核实过的真实回执及证据后才能继续。回执仍要通过收件人和关联标识校验；不存在的发送不能用手工编造的回执“补成功”。

## 边界

这不是群发系统、CRM 或无限轮次销售对话。每个子任务自动处理一条有效回复；后续回复会保存在事件收件箱供人工核对，不自动生成新报价或承诺。缺失邮箱、重复邮箱和拒收名单会显示为不可选，不静默丢弃。买家是否真实、采购资格是否足够仍取决于真实 Worker 的证据与人工审核，不由通过测试来证明。
