# 后续回复的人工跟进

场景：流程已经处理首条回复并结束，客户又补发了规格、数量或样品反馈。该事件仍存放在收件箱；v0.4 同时创建一个可追踪的人工待办。

## 进入条件

- 事件通过现有认证和数据契约校验；关联标识已绑定当前企业的原运行。
- 原运行为 COMPLETED、REJECTED、TIMED_OUT、FAILED 或 CANCELLED；事件尚未被消费。
- 接收时间不早于运行创建时间。买家回复的发件邮箱与原审批收件人一致。
- 样品事件依据原样品回执关联；不额外宣称样品信息的真实性。

错误发件人、未知关联、过早事件、NEEDS_RECONCILIATION 运行仍留在原处理路径，不生成销售跟进。若事件先收到，运行后关闭，路由刷新时补建。已有待办不会因重检、重复回调或重启而重置。

HMAC 和邮箱匹配仍不等于真实买家身份认证；来源验证由可信网关负责。

## 操作

1. 在“待跟进回复”查看原始事件和已有记录。用 operator 领取，成为负责人。
2. 填写下一步行动及未来期限。页面显示未领取、活动及逾期总数；列表有分页，统计不受单页上限影响。
3. 完成后写明处理结果，选择已处理；不需要跟进的可注明原因关闭。
4. 关闭后可重新打开，原负责人和期限保留。需要新期限时重新安排。

每次操作须提交当前 expectedVersion 和至少 10 个字符的实质说明。其他操作员不能覆盖负责人的记录；admin 可以留说明后接手。版本冲突返回 409，应重新读取记录再操作。

待办生成、修改、历史和审计在 SQLite 同一事务提交。每个企业每个事件只生成一条待办；历史保留原责任人、期限、状态、处理人和说明。

## API 例子

以下是字段结构，实际 ID、版本、时间和说明应来自真实任务：

```json
{
  "expectedVersion": 2,
  "action": "schedule",
  "note": "已与负责同事核对，下一步整理经审核的规格与报价。",
  "dueAt": "2026-12-01T08:00:00.000Z",
  "nextAction": "核对买家补充规格，准备待审核报价"
}
```

action 可为 claim、schedule、resolve、dismiss、reopen。只有 schedule 接受 dueAt/nextAction，且须先领取。

## 明确边界

本版是人工作业队列：不自动发邮件、不发送到期通知、不推进原已关闭流程、不创建新报价、不修改原预算、不自动计入商业成果。需要对外回复时走既有流程的发布与具体内容审批。取消旧运行也不代表忽略客户新来信，所以其有效来信仍生成待办，但不会恢复旧运行。

处理待办不会把事件升级为已消费事件，不能据此绕过成果账本中的 business_event 校验。确有新商业成果时，按原证据要求另行登记与独立审核。
